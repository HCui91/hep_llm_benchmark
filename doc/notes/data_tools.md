## 1. Rivet

**Current version.** Rivet 4.1.4, released 2026-09-10: https://gitlab.com/hepcedar/rivet/-/releases/rivet-4.1.4. Confirmed the 4.x line via the full release list (rivet-4.0.0 on 2024-02-29 through rivet-4.1.4): https://gitlab.com/api/v4/projects/hepcedar%2Frivet/releases. The Rivet 4 release note is a peer-reviewed paper: Bierlich et al., "Robust independent validation of experiment and theory: Rivet version 4 release note," SciPost Phys. Codebases 36 (2024), arXiv:2404.15984: https://arxiv.org/abs/2404.15984.

Note: `rivet.hepforge.org` is now bot-gated (Anubis anti-scraping challenge) and redirects to a new site, `https://heprivet.org/` (confirmed live by direct fetch on this machine, 2026-09-30) - `heprivet.org` states "over 2000 analyses have been preserved so far." The GitLab repository (`gitlab.com/hepcedar/rivet`) is the reliable machine-readable primary source for routine counts and history, not the doc-site mirror.

**Number of analysis routines.** Counted directly via the GitLab repository API tree listing of `analyses/` at HEAD (2026-09-30, close to the rivet-4.1.4 tag from 2026-09-10): **2075 `.info` files** (one per analysis routine), matching a research agent's independent count at the `rivet-4.1.4` tag of 2072 `.info` / 2069 `.cc` files, and consistent with `heprivet.org`'s "over 2000 analyses" claim. Query: `GET /api/v4/projects/hepcedar%2Frivet/repository/tree?path=analyses&recursive=true` (83 pages / ~8200 tree entries). Top-level layout is one `plugin<EXPERIMENT>/` directory per experiment (pluginATLAS, pluginCMS, pluginALICE, pluginLHCb, pluginBELLE, pluginD0, pluginHERA, etc.) confirmed at https://gitlab.com/hepcedar/rivet/-/tree/rivet-4.1.4/analyses.

**Linking routines to HEPData (.yoda) reference data.** Each analysis is a set of files sharing one basename, e.g. for `ATLAS_2019_I1750330`: `pluginATLAS/ATLAS_2019_I1750330.cc` (analysis code), `.info` (YAML metadata), `.plot` (plot styling), `.yoda.gz` (gzipped YODA reference data = the published measurement). Verified by fetching the real files, e.g. https://gitlab.com/hepcedar/rivet/-/raw/rivet-4.1.4/analyses/pluginATLAS/ATLAS_2019_I1750330.info. The `.info` file carries an `InspireID:` field linking to the paper; HEPData records are keyed by the same Inspire literature ID, and `rivet-mkanalysis` (the skeleton generator) uses that ID to auto-download the corresponding HEPData data tables into the bundled `.yoda` reference file, which is installed under `<installdir>/share/Rivet/` at build time. At runtime `Analysis::book()` calls that reference a HEPData table auto-load bin edges/values from this file.

**How routines are added.** Confirmed: development happens via GitLab merge requests against https://gitlab.com/hepcedar/rivet, fully browsable with dates via both the web UI (https://gitlab.com/hepcedar/rivet/-/merge_requests) and the public REST API, no auth needed. Examples fetched directly: MR !1264 "H1 DIS analyses ported from hztool - part 1", created 2026-06-09, merged 2026-09-18, explicitly names new routines H1_1999_I482053, H1_1997_I443753, H1_1996_I421030 (https://gitlab.com/hepcedar/rivet/-/merge_requests/1264); the 4.1.4 release notes list newly-added analyses LHCB_2019_I1730448, LHCB_2025_I2922449, ALICE_2024_I2848263, ALICE_2015_I1395253. Per-file commit history is also directly queryable, e.g. `GET /repository/commits?path=analyses/pluginATLAS/<name>.cc` returns exact timestamps. **This means a benchmark can select routines added after a given date by filtering merge/commit timestamps in the GitLab API - a concrete mechanism for avoiding memorised (pre-training-cutoff) routines.**

**Tools for comparing YODA histograms.** `yodadiff` - numeric diff of two YODA files, options include `-t/--tol` (relative tolerance), `-e/--errors`, `--normalize`, `-m/--match`/`-M/--unmatch` (regex path filters), `-d/--dev-histo` (deviation histogram), `--ignore-missing/--ignore-new/--ignore-types`; it reports numerical (mis)matches, not a chi2 by itself: source https://gitlab.com/hepcedar/yoda/-/raw/release-2-1-x/bin/yodadiff. `rivet-mkhtml` - builds an HTML comparison page from `.yoda` files (options `--refid`, `-m`/`-M`, `-c/--config`, `--no-ratio`, `-s/--single`, `--pdf/--ps`): https://manpages.debian.org/testing/rivet/rivet-mkhtml.1. Goodness-of-fit / chi2: the YODA plot-config system supports `GofLegend=<0|1>` and `GofType=<naiveChi2reduced|naiveChi2>`, explicitly documented as a "naive" chi2 that neglects the full covariance breakdown: https://gitlab.com/hepcedar/yoda/-/blob/release-2-1-x/doc/PlotConfig.md. The older TeX-based `rivet-mkhtml-tex` had equivalent `GofType=chi2`/`GofReference`/`GofLegend` options: https://gitlab.com/hepcedar/rivet/-/raw/rivet-4.1.4/doc/tutorials/makeplots.md.

**HepMC reuse.** Confirmed as the standard workflow: `rivet --analysis=ANALYSIS_NAME main.hepmc` runs Rivet on a previously-saved HepMC file, per the official Pythia8 manual's Rivet-usage page: https://pythia8.web.cern.ch/manuals/pythia8318/RIVETusage.html (which also notes the alternative of piping events through a Unix FIFO to avoid writing large files to disk). Rivet's own HepMC tutorial confirms reading HepMC2 or HepMC3 files/streams: https://gitlab.com/hepcedar/rivet/-/raw/rivet-4.1.4/doc/tutorials/hepmc.md. So "generate HepMC once, run Rivet many times on the same file" is an explicit, supported, normal pattern.

**Detector smearing support.** Confirmed via GitLab source tree at tag rivet-4.1.4: projections `Smearing.hh`, `SmearedJets.hh`, `SmearedParticles.hh`, `SmearedMET.hh` and tools `SmearingFunctions.hh`, `JetSmearingFunctions.hh`, `ParticleSmearingFunctions.hh`, `MomentumSmearingFunctions.hh`, `ExptSmearingFunctions.hh` under `include/Rivet/`. Analyses wrap truth-level Particle/Jet/MissingMomentum projections in Smeared* projections that apply user-supplied efficiency and kinematic-smearing functors (parameterised on eta/pT) to emulate detector effects without full simulation. Documented in Buckley & Gutschow, "Fast simulation of detector effects in Rivet," arXiv:1910.01637: https://arxiv.org/pdf/1910.01637 (bundled ATLAS/CMS Run 1/2 functions in `ExptSmearingFunctions.hh`). This is Rivet-internal functor-based smearing, usable for the search track; UNCONFIRMED whether there is a built-in Rivet-Delphes integration layer beyond this.

**CPU cost for ~1e6 Pythia8 events at 13 TeV.** Best citable number: "Open LHC Monte Carlo Event Generation" (arXiv:2605.12229, May 2026), Section 4: ATLAS's Open Event Generation averaged 232 HS23-seconds/event over two years, i.e. about 198 billion CPU-core-seconds for 12.8 billion generated events (using an average core benchmark of ~15 HS23): https://arxiv.org/abs/2605.12229. That works out to about 15.5 core-seconds/event on average, i.e. roughly 1.5e7 core-seconds (~4,300 core-hours) for 1e6 events - but this ATLAS-wide average is dominated by heavier NLO ME+PS-matched samples (e.g. MadGraph5_aMC@NLO+Pythia8 showering), not plain LO Pythia8. UNCONFIRMED / order-of-magnitude estimate: pure LO Pythia8 generation (shower+hadronize only, e.g. inclusiveQCD/minbias-like processes) typically runs at low tens of milliseconds per event on a single core, which would put 1e6 events at roughly 1e4-1e5 core-seconds (minutes to a few hours single-core) - no authoritative citable number was found for this specific case, so treat it as reasoned estimate rather than a citation. Recommend citing the ATLAS-average figure as the one hard number available, with the pure-Pythia8 estimate flagged as UNCONFIRMED.

## 5. IRIS-HEP Analysis Grand Challenge (AGC)

**What it is.** The Analysis Grand Challenge is an IRIS-HEP integration exercise testing whether a full columnar physics-analysis workflow (data extraction, event filtering, observable construction, systematics, histogramming, statistical inference) scales to HL-LHC data volumes. It combines a fixed analysis-task specification on public Open Data with reference implementations exercising tools such as Rucio, ServiceX, coffea, awkward-array, RDataFrame, cabinetry and pyhf.
Sources: https://iris-hep.org/projects/agc.html , https://agc.readthedocs.io/en/latest/ , https://iris-hep.org/analysis-grand-challenge.html

**The ttbar cross-section task.** Measures the ttbar production cross-section in the single-lepton (semi-leptonic) channel using **2015 CMS Open Data** (not ATLAS). The top quark is reconstructed via a trijet system (observable m_bjj) in the signal region, with H_T used in a control region. The statistical model (pyhf/HistFactory) treats the ttbar cross-section as the parameter of interest, with nuisance parameters for jet pT scale/resolution (+/-3%), b-tagging, W+jets normalisation (+/-2.5%), luminosity (+/-3%), and ttbar ME/PS/scale variations. A secondary, smaller AGC task measures H->ZZ* using ATLAS Open Data.
Sources: https://agc.readthedocs.io/en/latest/taskbackground.html , https://github.com/iris-hep/analysis-grand-challenge/tree/main/analyses/cms-open-data-ttbar , https://arxiv.org/abs/2304.05214

**Reference implementations.**
- Main repo (task spec + reference pipelines): https://github.com/iris-hep/analysis-grand-challenge
  - coffea-based (Python, primary reference): https://github.com/iris-hep/analysis-grand-challenge/tree/main/analyses/cms-open-data-ttbar
  - ROOT RDataFrame-based: https://github.com/root-project/analysis-grand-challenge
  - Other community ports: Julia (https://github.com/Moelf/LHC_AGC.jl), columnflow (https://github.com/columnflow/agc_cms_ttbar)
- Versioned release on Zenodo (v0.2.0): https://zenodo.org/records/7799436

**Metrics and suitability as a reference task.** AGC's published metrics are mainly runtime/scaling benchmarks - wall-clock time, throughput, scalability across facilities - documented in "First performance measurements with the Analysis Grand Challenge" (ACAT 2022): https://arxiv.org/abs/2304.05214, with a later update at https://arxiv.org/pdf/2609.19753 (extends benchmarks, adds Combine/HS3 integration). No published numeric "correctness tolerance" for the physics result was found; the docs validate results qualitatively (top-mass peak near 173 GeV, BDT jet-assignment accuracy, post-fit pull plots): https://agc.readthedocs.io/en/latest/taskbackground.html.

Because the task is fully specified - fixed CMS Open Data files, a fixed HistFactory workspace, open reference code with specific output histograms/fit results - it **could serve as a ready-made reference task with a de-facto known answer** for scoring whether an agent reproduces a known analysis end to end. UNCONFIRMED: no evidence found that AGC has already been used to benchmark AI/LLM agents; this would be a novel application, not an existing precedent.

## 6. HiggsML challenges

**2014 Kaggle HiggsML challenge.** Dataset: ATLAS-simulated Higgs->tau tau signal vs. Z->tau tau, ttbar and W+jets backgrounds; 818,238 events, 30 variables, each event weighted to reflect 2012-like conditions. Hosted on the CERN Open Data Portal, CC0 licence: http://opendata.cern.ch/record/328 (DOI 10.7483/OPENDATA.ATLAS.MQ5J.GHXA), documentation record http://opendata.cern.ch/record/329. Original competition (250k-event subset) ran on Kaggle 14 May - 15 Sep 2014: https://www.kaggle.com/c/higgs-boson.

AMS (Approximate Median Significance) metric: AMS(s,b) = sqrt(2[(s+b+b_reg)*ln(1+s/(b+b_reg)) - s]), with regularisation constant b_reg = 10, s and b being weighted sums of true-positive and false-positive events passing a selection. The formula is corroborated in secondary arXiv papers citing the challenge (e.g. https://arxiv.org/pdf/1412.2106, https://arxiv.org/pdf/1409.2655); UNCONFIRMED whether the CERN Open Data page itself reproduces the formula verbatim. Original paper: Adam-Bourdarios, Cowan, Germain, Guyon, Kegl, Rousseau, "The Higgs boson machine learning challenge", JMLR: Workshop and Conference Proceedings vol. 42, pp. 19-55 (2015): http://proceedings.mlr.press/v42/cowa14.pdf. UNCONFIRMED: no separate arXiv preprint of this paper was found.

**FAIR Universe HiggsML Uncertainty Challenge.** Hub: https://fair-universe.lbl.gov/ and results page https://fair-universe.lbl.gov/Higgs-Uncertainty-Challenge.html. Official NeurIPS 2024 Competition Track event, launched on Codabench 1 Oct 2024, ran through ~March/May 2025, winners announced 8 May 2025: https://www.codabench.org/competitions/2977/ , https://neurips.cc/virtual/2024/competition/84792. Dataset: ~280 million simulated pp-collision events (ATLAS-like, Pythia 8.2 + Delphes 3.5.0), signal = H->tau tau (one leptonic, one hadronic tau), backgrounds Z->tau tau, ttbar, diboson - about 1000x the 2014 dataset. Public dataset on Zenodo: https://zenodo.org/records/15131565.

Metric: a "Coverage Score" combining (1) average 68.27% confidence-interval width w = (1/N) * sum(|mu_84,i - mu_16,i|) and (2) empirical coverage probability c (fraction of test cases where the true mu falls inside the predicted [mu_16, mu_84] interval), combined as score = -ln((w+eps)*f(c)) with eps = 1e-2 and f(c) an asymmetric penalty punishing under-coverage more than over-coverage. Source (challenge design paper): https://arxiv.org/abs/2410.02867. 2025 results paper: "Fair Universe HiggsML Uncertainty Challenge" (arXiv:2509.22247, CC-BY 4.0): https://arxiv.org/abs/2509.22247.

**Public data and code.** 2014 challenge: data public on CERN Open Data Portal (CC0), http://opendata.cern.ch/record/328; competition page still listed on Kaggle (no live scoring server), https://www.kaggle.com/c/higgs-boson. FAIR Universe challenge: data public on Zenodo, https://zenodo.org/records/15131565; scoring/ingestion code and starting kit public on GitHub, https://github.com/FAIR-Universe/HEP-Challenge; competition platform Codabench #2977, https://www.codabench.org/competitions/2977/; docs at https://fair-universe.lbl.gov/docs/. UNCONFIRMED: explicit OSS licence of the FAIR-Universe/HEP-Challenge GitHub repo was not visible in the README fetched.

**LHCO2020 R&D dataset and Black Boxes 1-3.** Summary/community paper: "The LHC Olympics 2020: A Community Challenge for Anomaly Detection in High Energy Physics", arXiv:2101.08320 (Rep. Prog. Phys. 84 124201, 2021): https://arxiv.org/abs/2101.08320. R&D dataset (Kasieczka, Nachman, Shih) on Zenodo: 1M QCD dijet background events plus a benchmark W'->XY signal (100k events, X,Y->qq), Pythia8+Delphes, HDF5: https://doi.org/10.5281/zenodo.2629072. Black-box datasets on Zenodo: https://doi.org/10.5281/zenodo.3547721.

Per arXiv:2101.08320 (verified in the full text):
- Black Box 1: signal = Z'->XY, X->qq, Y->qq; mZ'=3.823 TeV, mX=732 GeV, mY=378 GeV; 834 signal events out of 1M total. Released 19 Nov 2019 ("Winter Olympics").
- Black Box 2: **background only, no injected signal** - generated with Herwig++ instead of Pythia and a modified Delphes card.
- Black Box 3: signal = KK-graviton at m=4.2 TeV with two decay modes (dijet-like and a radion channel, mR=2.217 TeV, R->gg); 1200 dijet + 2000 trijet-topology signal events.

Recent dataset extensions (2026): "Extension of the LHC Olympics 2020 R&D Dataset" (Fanselow), higher-pT background sample, 22.5M Pythia + 10M Herwig QCD dijet events, https://zenodo.org/records/22685072; "Additional Signal Models for the LHCO2020 R&D" (Das et al.), four new signal topologies supporting arXiv:2604.20965, https://zenodo.org/records/18983506.

**How results were revealed.** Black Box 1 ("Winter Olympics") results presented at ML4Jets2020, NYU, 15-17 Jan 2020: https://indico.cern.ch/event/809820/sessions/329216/. Black Boxes 2 and 3 ("Summer Olympics") unblinded at the Anomaly Detection Mini-Workshop, DESY, 16-17 July 2020: https://indico.desy.de/event/25341/ (summary talk https://indico.desy.de/event/25341/contributions/56822/attachments/36777/45997/SummaryAnomalyDetectionWorkshopJuly2020.pdf). Full method comparison in arXiv:2101.08320.

**Dark Machines Anomaly Score Challenge.** "The Dark Machines Anomaly Score Challenge: Benchmark Data and Model Independent Event Classification for the Large Hadron Collider", arXiv:2105.14027 (SciPost Physics): https://arxiv.org/abs/2105.14027. Unsupervised-ML challenge to find new physics without assuming a specific model; benchmark dataset of over 1 billion simulated 13 TeV pp events at 10 fb^-1.

**Newer (2023-2026) challenges.** No new formally-run blind-submission "challenge" (analogous to LHCO2020 or Dark Machines) was found for 2023-2026 - UNCONFIRMED / likely does not exist. What continues is dataset extension of LHCO2020 itself (2026 Zenodo records above) and ongoing use of LHCO2020 as a standing research benchmark (e.g. arXiv:2609.00132; JHEP02(2026)254: https://link.springer.com/article/10.1007/JHEP02(2026)254). CATHODE and successor methods (ANODE, SALAD, FETA, CURTAINS) are algorithms benchmarked on LHCO2020 data, not separate formal challenges. ML4Jets remains the recurring community venue (e.g. ML4Jets2024, LPNHE Paris, 4-8 Nov 2024: https://indico.cern.ch/event/1386125/).

## 8. Recasting tools

**MadAnalysis5 PAD (Public Analysis Database).** MadAnalysis5 is a C++ framework for phenomenological collider analyses, including reinterpretation/recasting of LHC results: https://madanalysis.irmp.ucl.ac.be/ , project page https://cp3.irmp.ucl.ac.be/projects/madanalysis. PAD is a database of community-contributed recast ATLAS/CMS analyses implemented in the MA5 framework: https://madanalysis.irmp.ucl.ac.be/wiki/PublicAnalysisDatabase. Code: https://github.com/MadAnalysis/madanalysis5 (public, e.g. release v1.11.2: https://github.com/MadAnalysis/madanalysis5/releases/tag/v1.11.2).

**CheckMATE.** Site: https://checkmate.hepforge.org/. Public code: https://github.com/CheckMATE2/checkmate2. Takes simulated MC events for a BSM model, runs detector simulation plus implemented ATLAS/CMS analyses, and reports excluded/allowed status. Key paper (CheckMATE 2): arXiv:1611.09856, https://arxiv.org/pdf/1611.09856. Also implements full/simplified likelihoods: https://link.springer.com/article/10.1140/epjc/s10052-026-15414-8.

**SModelS.** Site: https://smodels.github.io/, code https://github.com/SModelS/smodels. Public and actively maintained (v3, arXiv:2409.12942: https://arxiv.org/pdf/2409.12942). Decomposes a full BSM model into simplified-model topologies with signal weights and compares against a database of ATLAS/CMS simplified-model results (including some obtained by recasting), without needing dedicated MC simulation. Can use ATLAS/CMS pyhf full-likelihood JSONs via an interface described in arXiv:2009.01809: https://arxiv.org/pdf/2009.01809.

**Contur.** Web page https://hepcedar.gitlab.io/contur-webpage/, docs https://hepcedar.gitlab.io/contur-webpage/codedocs/running.html, public GitLab repo https://gitlab.com/hepcedar/contur (active, many releases). Uses Rivet-based unfolded SM measurements to set "due diligence" constraints on new-physics models - a rapid, model-independent check rather than a dedicated search recast.

**HEPData full likelihoods / pyhf JSON.** HEPData search for pyhf-tagged records: https://www.hepdata.net/search/?q=pyhf. ATLAS has published full HistFactory likelihoods as pyhf JSON on HEPData for a growing set of Run-2 searches (confirmed via literature describing CheckMATE's automatic download of these files from HEPData, e.g. https://link.springer.com/article/10.1140/epjc/s10052-026-15414-8, which mentions 9 ATLAS and 4 CMS searches with JSON likelihoods available). pyhf itself: https://github.com/scikit-hep/pyhf.

Which tool suits a "human reference implementation" for the search track: where an official pyhf JSON full likelihood exists on HEPData for the relevant analysis, that is the strongest ground truth (the experiment's own statistical model, not a third-party recast). Where none exists, SModelS (fast, simplified-model database) and MadAnalysis5-PAD/CheckMATE (full MC recast reproducing an analysis' cutflow/signal-region yields) are the standard community reference implementations. Contur is less suited to the search track since it targets precision SM measurements rather than dedicated search regions.
